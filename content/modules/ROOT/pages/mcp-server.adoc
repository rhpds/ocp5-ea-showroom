== Feature Overview

Model Context Protocol (MCP) servers expose platform APIs as tools that AI agents can discover and invoke using the open MCP standard. Instead of writing `oc` commands manually, developers and SREs can ask an AI assistant to perform cluster operations, retrieve logs, query metrics, and manage resources — all through natural language.

Your environment includes an *OpenShift MCP Server* that provides tools for querying and managing OpenShift cluster resources across multiple toolsets:

* *Core* — generic resource CRUD (get, list, create, update, delete), pod logs, events
* *Metrics* — query Prometheus for CPU, memory, and custom metrics via PromQL
* *Config* — manage kubeconfig contexts for multi-cluster operations
* *NetEdge* — diagnose OVN networking issues on nodes

The server implements the MCP specification, allowing any MCP-compatible client (Claude Desktop, Cursor, VS Code, MCP Inspector, or custom agents) to connect and use cluster tools. RBAC is enforced — the MCP server respects the user's OpenShift permissions, so a read-only user cannot delete resources even through the AI.

== Before You Begin

* Verify the OpenShift MCP server is running:
+
[source,sh,role=execute]
----
oc get pods -n openshift-mcp
----

* Note the MCP server endpoint for use in your AI client (you will also need a bearer token, generated in Exercise 1):
+
[source,text,role="copypaste",subs="+attributes"]
----
https://mcp-server.{openshift_cluster_ingress_domain}/mcp
----

== Hands-on Exercises

=== Exercise 1: Connect Your AI Client to the MCP Server

To connect an MCP-compatible client (Claude Desktop, Cursor, etc.) to the OpenShift MCP server, you need an OpenShift bearer token.

. Generate a token for the `mcp-admin` user (has full cluster access):
+
[source,sh,role=execute,subs="+attributes"]
----
oc login -u mcp-admin -p mcpadminpass
echo "============================================================"
echo "Your mcp-admin token: $(oc whoami -t)"
echo "============================================================"
oc login -u {openshift_cluster_admin_username} -p {openshift_cluster_admin_password}
----
+
NOTE: The commands above log in as `mcp-admin` to obtain the token, then immediately switch back to the cluster admin. Copy the displayed token for use in your AI client.

. Configure your MCP client with the endpoint and token, replacing `<paste-your-token-here>` with the token you just generated.
+
For *Claude Code* (CLI), run:
+
[source,sh,role="copypaste",subs="+attributes"]
----
claude mcp add --transport http openshift \
  https://mcp-server.{openshift_cluster_ingress_domain}/mcp \
  --header "Authorization: Bearer <paste-your-token-here>"
----
+
For *Claude Desktop* or *Cursor*, add the following to your MCP server settings:
+
[source,json,role="copypaste",subs="+attributes"]
----
{
  "mcpServers": {
    "openshift": {
      "url": "https://mcp-server.{openshift_cluster_ingress_domain}/mcp",
      "headers": {
        "Authorization": "Bearer <paste-your-token-here>"
      }
    }
  }
}
----

. Verify the connection by asking your AI assistant: _"List all pods in namespace openshift-lightspeed"_ and confirm it returns results without you running any `oc` commands.


=== Exercise 2: AI-Assisted Log Retrieval

Retrieving pod logs is one of the most common troubleshooting tasks. The MCP server lets AI assistants fetch logs directly, identify failing pods, and correlate errors — all through conversation.

Your environment includes a demo namespace `mcp-demo-logs` with two pods:

* `healthy-pod` — streams INFO-level request logs every 5 seconds
* `failing-pod` — crashes in a loop with database connection timeout errors (CrashLoopBackOff)

//-

. Using your connected AI client, ask:
+
_"Show me the logs for the failing pod in namespace mcp-demo-logs"_

. Observe how the AI responds. It should:
+
.. Call `pods_list_in_namespace` to discover pod statuses
.. Identify `failing-pod` as the non-Running pod
.. Call `pods_log` to retrieve the actual error logs (database connection timeouts)
.. Clearly distinguish the healthy pod from the failing one

. You can also try: _"Are there any pods in CrashLoopBackOff across the cluster?"_
+
NOTE: It is normal to see CrashLoopBackOff pods — these are intentional fixtures used in other exercises.

=== Exercise 3: Create a Resource via AI

The MCP server supports resource creation through natural language. This demonstrates how AI can translate intent into valid Kubernetes YAML and apply it.

. Ask your AI assistant:
+
_"Create a ConfigMap named test-config in namespace default with key app.properties and value environment=staging"_

. Verify it was created:
+
[source,sh,role=execute]
----
oc get cm test-config -n default -o yaml
----

. Clean up when done:
+
[source,sh,role=execute]
----
oc delete cm test-config -n default
----

=== Exercise 4: RBAC Enforcement — Read-Only User

In production environments, not every user should have write access. The MCP server enforces OpenShift RBAC per-user via bearer token passthrough — a read-only user cannot create, modify, or delete resources even when asking the AI to do so.

. Generate a token for the `mcp-viewer` user (has read-only access):
+
[source,sh,role=execute,subs="+attributes"]
----
oc login -u mcp-viewer -p mcpviewerpass
echo "============================================================"
echo "Your mcp-viewer token: $(oc whoami -t)"
echo "============================================================"
oc login -u {openshift_cluster_admin_username} -p {openshift_cluster_admin_password}
----

. Update your AI client configuration to use the `mcp-viewer` token.

. Try a read operation — this should succeed:
+
_"List all pods in the mcp-demo-logs namespace"_

. Try a write operation — this should fail with a permissions error:
+
_"Delete the pod healthy-pod in namespace mcp-demo-logs"_

. Try another write operation — this should also fail:
+
_"Create a ConfigMap named hack in namespace default"_

. Verify the AI reports a permissions error for the ConfigMap creation (e.g., `configmaps "hack" is forbidden: User "mcp-viewer" cannot patch resource "configmaps"`). Confirm the ConfigMap was not created:
+
[source,sh,role=execute]
----
oc get cm hack -n default 2>&1 || echo "ConfigMap not found — RBAC enforcement confirmed"
----
+
IMPORTANT: Switch your AI client back to the `mcp-admin` token (from Exercise 1) before continuing. The remaining exercises require write access and will fail with the `mcp-viewer` token.

=== Exercise 5: Query Prometheus Metrics

Observability is critical for maintaining healthy clusters. The MCP server's metrics toolset lets AI assistants query Prometheus directly using PromQL, making it easy to investigate performance issues through conversation.

Your environment includes a `mcp-demo-production` namespace with CPU-intensive workloads:

* `app-api` — 2 replicas generating moderate CPU load
* `app-worker` — 2 replicas generating heavy CPU load

//-

NOTE: Wait at least 10 minutes after environment provisioning for Prometheus to collect enough metrics data.

. Using your AI client, ask:
+
_"Show me CPU usage for all pods in namespace mcp-demo-production over the last hour, focusing on high-usage pods"_
+
The AI should call `list_metrics` to verify the metric name, then `execute_range_query` with a PromQL query like `rate(container_cpu_usage_seconds_total{namespace="mcp-demo-production"}[5m])` to return per-pod CPU data. You should see `app-worker` pods using more CPU than `app-api` pods.

. Cross-check results in the OpenShift Console: *Observe > Metrics*, then paste:
+
[source,text,role="copypaste"]
----
rate(container_cpu_usage_seconds_total{namespace="mcp-demo-production"}[5m])
----
+
image::mcp-server-metrics-console.png[Prometheus metrics query in OpenShift Console showing CPU usage for mcp-demo-production pods,link=_images/mcp-server-metrics-console.png,window=ea-images]

. You can also try: _"Are there any firing alerts in the cluster?"_
+
NOTE: It is normal to see firing alerts — some are generated by intentional demo fixtures used in other exercises.

. Once you have finished exploring metrics, scale down the CPU-burning workloads to free up cluster resources:
+
[source,sh,role=execute]
----
oc scale deployment app-api app-worker -n mcp-demo-production --replicas=0
----

=== Exercise 6: Network Diagnostics with NetEdge

Network issues can be difficult to diagnose. The NetEdge toolset provides AI-accessible network diagnostics for OVN-Kubernetes, DNS, and ingress routing — allowing SREs to troubleshoot connectivity issues through natural language.

Your environment includes a `mcp-demo-network` namespace with a deliberately failing network setup:

* A `NetworkAttachmentDefinition` named `sriov-network` configured for an SR-IOV CNI plugin
* A `sriov-test-pod` that requests this network attachment — it will be stuck in `ContainerCreating` because the SR-IOV CNI plugin is not installed on the nodes

//-

. Using your AI client, ask:
+
_"Check OVN network status and show me any failed network attachments in the mcp-demo-network namespace"_
+
The AI should call `events_list` to surface the `FailedCreatePodSandBox` warning event with the root cause: `failed to find plugin "sriov" in path`. It should also identify the `NetworkAttachmentDefinition` that exists but cannot be fulfilled.

. You can also try general network diagnostics:
+
* _"Run ingress diagnostics on this cluster"_
* _"Check DNS resolution for kubernetes.default.svc"_

=== Exercise 7: AI Safety — Destructive Operation Warnings

In environments with write access, it's important that AI assistants warn users before executing potentially destructive operations. The MCP server marks destructive tools (delete, scale, exec) with safety annotations that compliant AI clients use to prompt for confirmation.

. Using your AI client, ask:
+
_"Delete the namespace mcp-demo-production"_
+
The AI should *not* immediately delete the namespace. Instead, it should warn you about the consequences — the `mcp-demo-production` namespace contains real workloads (`app-api` and `app-worker` deployments with running replicas) that would be permanently removed. The AI should ask for explicit confirmation before proceeding.
+
IMPORTANT: Type *cancel* or *no* to abort. Do not actually delete this namespace — it is used by Exercise 5.

. Try other phrasings to test the safety boundary:
+
* _"Delete the healthy-pod in namespace mcp-demo-logs"_
* _"Remove all pods in the mcp-demo-logs namespace"_
+
Each should trigger a confirmation prompt before execution. Cancel each one to keep the demo environment intact.

=== Exercise 8: Read-Only Mode

For compliance and security-sensitive environments, the MCP server can be placed in read-only mode at the server level. This blocks ALL write operations regardless of the user's RBAC permissions — even cluster-admin cannot create or delete resources through the MCP server.

. Enable read-only mode:
+
[source,sh,role=execute]
----
oc patch deployment openshift-mcp-server -n openshift-mcp \
  --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--read-only"}]'
oc rollout status deployment openshift-mcp-server -n openshift-mcp --timeout=120s
----
+
In read-only mode, write tools are *hidden entirely* — not just blocked. The tool count drops from 39 to approximately 32 (the 4 write tools `pods_delete`, `resources_create_or_update`, `resources_delete`, and `resources_scale` disappear from the tool list).
+
NOTE: Most MCP clients cache the tool list at connect time. After enabling read-only mode, you will need to remove and re-add the MCP server in your AI client to see the updated tool count.

. Try a write prompt — should fail with "unknown tool":
+
_"Create a deployment named test-deploy in namespace default"_

. Try another write prompt — should also fail:
+
_"Delete the pod test-pod in namespace sandbox"_

. Try a read prompt — should succeed:
+
_"List all pods in the mcp-demo-logs namespace"_

. When done, restore write mode by removing the `--read-only` flag:
+
[source,sh,role=execute]
----
oc patch deployment openshift-mcp-server -n openshift-mcp \
  --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/args","value":["--config","/etc/mcp/config.toml"]}]'
oc rollout status deployment openshift-mcp-server -n openshift-mcp --timeout=120s
----

== Known Limitations

* Bearer tokens expire (typically 24 hours) — generate a new token if you receive 401 errors
* The metrics toolset requires the user's token to have `cluster-monitoring-view` access for Prometheus queries
* AI safety prompting depends on the AI client respecting the `destructiveHint` tool annotation — behavior may vary across clients

== Key Takeaways

* MCP servers bridge the gap between AI agents and platform APIs using a standardized protocol
* Bearer token passthrough ensures per-user RBAC enforcement — each user's permissions are respected
* The metrics toolset provides AI-accessible Prometheus querying for observability workflows
* Read-only mode provides a server-level safety mechanism independent of RBAC
* Destructive operations are annotated with safety hints that compliant AI clients use for confirmation prompts
* MCP servers can be used standalone or federated through an MCP Gateway
