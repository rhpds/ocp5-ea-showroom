== Feature Overview

Red Hat Advanced Cluster Security (ACS) 5 introduces several new capabilities for securing containerized and virtualized workloads:

* *VM Vulnerability Management* — extends RHACS vulnerability scanning to cover virtual machine workloads running on OpenShift Virtualization. The `roxagent` binary runs inside VMs, scans installed packages (RPM/DNF), and reports vulnerabilities to ACS Central via the collector relay over VSOCK. Organizations gain unified vulnerability visibility across both containers and VMs from a single ACS console.

* *File Activity Monitoring (FAM)* — provides runtime file integrity monitoring. Security teams can define custom file paths (with wildcard support) to monitor for access, modification, and rename operations. File activity criteria can be combined with process-level criteria (process name, ancestor, arguments, UID) in deployment and node policies, enabling detection of unauthorized file access patterns required for compliance frameworks such as PCI-DSS.

* *Init Container Security Coverage* — RHACS now evaluates init containers for both image scanning and security policies. When a deployment references init containers, their images are scanned for vulnerabilities using the same process as main container images. Build and Deploy stage policies can be configured to include or exclude init containers using the "Filters" menu.

* *ACS MCP Server* — exposes ACS Vulnerability Management and Configuration Management APIs as MCP tools, allowing AI agents to interact programmatically with security data.

== Hands-on Exercises

=== Exercise 5: Init Container Security Coverage

This exercise will walk you through and demonstrate the capabilities in OCP5 and RHACS (5) for the scanning of Init Containers.

Init Containers are standalone containers executed as part of a Kubernetes deployment. They occur before the actual Pods of the deployment are created, and are used
to perform various initialisation tasks needed by the Pod, namely operations like file initialisation, DB population and the like.

As such they are an attack vector for exploitation; RHACS now has capabilities for scanning and acting upon exploits.

Unlike Pods, Init Containers are not resident; once executed they are removed, so the runtime policies offered by RHACS focus on process execution and baseline comparisons.

For this exercise we will be using the OCP and RHACS interfaces.

== Using OpenShift Lightspeed and the OpenShift User Interface to prepare the tests

In the OpenShift lightspeed dialog, enter the following:

[source,role="copypaste"]
----
create a new project for me called acs-init-container-test
----

The MCP server requires approval, so approve when it asks you.

On the left hand navigation, choose 'Projects' and then acs-init-container-tests. All of the examples will be executed in this project to allow you to observe the results simply in
the ACS console.

Now click on the '>_' icon at the top right to open the integrated console in the User Interface. We will use this to interact with the project for simplicities sake.

In the terminal type:

[source,bash,role="copypaste"]
----
oc project acs-init-container-test
----

Check the project has no workloads using:

[source,bash,role="copypaste"]
----
oc get pods
----

== Enabling Privileged access for the tests

In the console, type:

[source,bash,role="copypaste"]
----
oc adm policy add-scc-to-user privileged system:serviceaccount:acs-init-container-test:default
----

This allows Pods, and Init Containers, to switch to Privileged to perform actions.

== Running the tests without detection policies in place

For the sake of testing we have four specific use-cases represented by different Deployment definitions, each designed to highlight a behaviour now offered within
RHACS for the monitoring and actioning of Init Containers. These are:

.. 'Clean' deployment - runs an Init Container that has nothing out of the ordinary in it
.. 'Dirty' deployment - runs an Init Container that does something that is a violation
.. 'Blue' deployment - runs an Init Container that performs a Privileged action that has justification 
.. 'Red' deployment - runs an Init Container that uses an unpatched Image with known CVEs and performs a Privileged action that has no justification

== Key Takeaways

* ACS 5 extends security coverage beyond containers to virtual machines running on OpenShift Virtualization
* roxagent communicates with the collector via VSOCK, requiring no network configuration inside the VM
* File activity monitoring provides visibility into security-relevant file access patterns
* The ACS MCP server enables AI agents to query and act on security data programmatically
