= Agentic Troubleshooting

== Feature Overview

Agentic Troubleshooting combines OpenShift Lightspeed with OCP 5's agentic operator to provide AI-driven investigation and remediation of cluster and application issues. It operates in two modes:

* *User-initiated* — An SRE uses Lightspeed chat in _troubleshooting mode_ to investigate issues through natural language. The AI queries cluster state via MCP, correlates metrics and logs, and provides a mitigation plan. It can also dynamically generate inline Perses charts for visualization, which can be exported to dedicated dashboards.

* *Autonomous (agentic)* — The Alertmanager adapter monitors critical alerts and automatically triggers background investigations. The agent produces a step-by-step remediation plan in a "Proposed" state. An operations lead reviews findings in the Agentic Runs UI and authorizes execution with a single click.

Your environment includes pre-deployed applications with intentional issues designed to exercise these workflows:

[cols="2,1,1,2",options="header"]
|===
| Alert | Namespace | Severity | Scenario

| `PaymentErrorRateHigh` | payments | Critical | Database connection exhaustion causing 5xx errors
| `PostgresqlTooManyConnections` | payments | Warning | Connection pool leak in reporting-service
| `PodDisruptionBudgetLimit` | inventory | Critical | PDB minAvailable exceeds available pods
| `CatalogServicePodNotReady` | catalog-service | Warning | Pod stuck in not-ready state
| `UserImportPodNotScheduled` | user-imports | Warning | Pod pending due to unsatisfiable nodeSelector
|===

These issues are designed to leave a causal trail — cascading failures with an underlying root cause — rather than isolated symptoms. The agentic system will explore this trail, correlating metrics, logs, and resource state to identify the root cause and propose targeted remediation.

== Hands-on Exercises

=== Exercise 1: Investigate a Timeout Issue (User-Initiated)

In this exercise, you will test Lightspeed's ability to troubleshoot a cluster issue that does not have an associated Prometheus alert — a timeout connection problem in the `service-mesh` namespace, where a frontend pod is failing to reach a backend service due to a misconfigured NetworkPolicy.

. Open the OpenShift console and navigate to *Observe > Metrics* to get familiar with the current state. Try running this example query to see the top CPU consumers:
+
[source,text,role="copypaste"]
----
topk(10,
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])
  )
)
----
+
image::agentic-troubleshooting-metrics-console.png[Observe Metrics UI,link=_images/agentic-troubleshooting-metrics-console.png,window=ea-images]

. Open the OpenShift Lightspeed chat by clicking the chat icon in the bottom right of the console.

. Select the *troubleshooting* mode from the mode selector.
+
image::agentic-troubleshooting-mode-selector.png[Lightspeed troubleshooting mode selector,link=_images/agentic-troubleshooting-mode-selector.png,window=ea-images]

. Ask Lightspeed to investigate the timeout issue:
+
_"Investigate the timeout connection in the service-mesh namespace"_
+
Lightspeed will query the MCP server, examine pod logs and events, and identify the root cause — a NetworkPolicy blocking the frontend from reaching the backend service.
+
NOTE: During investigation, Lightspeed may prompt you to approve certain tools such as `pod_exec`. More powerful tools require explicit approval before the agent can use them. Click *Approve* to allow Lightspeed to proceed. It is normal for `pod_exec` to occasionally fail — security-hardened pods on OpenShift use minimal container images that may not include common shell utilities like `ss`, `netstat`, or `dig`. Lightspeed uses any available signals from a wide range of components (pod logs, events, Prometheus metrics, resource state) to analyze and correlate issues, so a failed exec does not prevent a successful investigation.
+
image::agentic-troubleshooting-tool-approval.png[Tool approval prompt in Lightspeed,link=_images/agentic-troubleshooting-tool-approval.png,window=ea-images]

. Continue the conversation with follow-up prompts:
+
_"Identify recent changes that may have caused this and suggest remediation"_

. Review the mitigation plan that Lightspeed provides. It should include correlation evidence and a read-only remediation plan.
+
image::agentic-troubleshooting-mitigation-plan.png[Lightspeed mitigation plan output,link=_images/agentic-troubleshooting-mitigation-plan.png,window=ea-images]
+
NOTE: Do not execute the remediation steps manually. In Exercise 4, the agentic system will provide a more structured way to review and execute remediation plans with full audit trails.

This conversational approach to troubleshooting means SREs can investigate complex issues without memorizing `oc` commands, PromQL syntax, or navigating between multiple console views. Lightspeed handles the tool orchestration while the SRE focuses on understanding the problem and deciding what to do about it.

=== Exercise 2: Investigate a Critical Alert (User-Initiated)

This exercise validates Lightspeed's ability to correlate standard infrastructure alerts and provide actionable remediation guidance.

. Recall from the *Before You Begin* section that the `PodDisruptionBudgetLimit` alert is firing in the `inventory` namespace. In this exercise, we will ask Lightspeed to investigate it.

. Open the Lightspeed chat (in *troubleshooting* mode) and ask it to investigate the alert:
+
_"Investigate the root cause of the firing PodDisruptionBudgetLimit alert"_
+
Lightspeed will use multiple tools, examine pod state and logs, correlate Prometheus metrics, and identify the root cause (a typo in the image tag `laetst` — it should have been `latest`).

. Review the response. Lightspeed should provide a mitigation plan based on relevant in-cluster data points — Kubernetes resource state, pod logs, and Prometheus metrics.
+
image::agentic-troubleshooting-alert-investigation.png[Lightspeed alert investigation results,link=_images/agentic-troubleshooting-alert-investigation.png,window=ea-images]

Whether the starting point is a firing Prometheus alert or a vague symptom like "things are slow," Lightspeed follows the same investigative process — correlating multiple data sources to surface the root cause. This makes it equally effective for known alerts and novel issues that don't yet have monitoring coverage.

=== Exercise 3: Generate Inline Perses Charts (User-Initiated)

OpenShift Lightspeed can dynamically generate interactive Perses charts directly in the chat UI, making it easy to visualize metrics during a troubleshooting session.

. First, create a Perses dashboard to receive exported charts. Navigate to *Observe > Dashboards (Perses)* and click *Create* to create a new dashboard named `Investigation Hub`. Select the `payments` namespace.
+
image::agentic-troubleshooting-create-dashboard.png[Creating a Perses dashboard,link=_images/agentic-troubleshooting-create-dashboard.png,window=ea-images]

. In the Lightspeed chat (still in *troubleshooting* mode), ask for a visualization related to your current investigation:
+
_"Show me the most relevant charts for this investigation"_
+
Or create charts from scratch with specific prompts:
+
_"Which pods are using the most CPU? Show me the top 5. Use Prometheus and visualize."_
+
_"Which pods were crashlooping in the last 5 minutes? Use Prometheus and visualize."_

. Verify that an interactive Perses chart is rendered directly in the chat UI.
+
image::agentic-troubleshooting-perses-inline.png[Inline Perses chart in Lightspeed chat,link=_images/agentic-troubleshooting-perses-inline.png,window=ea-images]

. Click the *Add To Dashboard* button on the chart to export it to your `Investigation Hub` dashboard. The chart is now persisted and can be revisited at any time under *Observe > Dashboards (Perses)* to see updated metrics.
+
image::agentic-troubleshooting-add-to-dashboard.png[Add To Dashboard button on inline Perses chart,link=_images/agentic-troubleshooting-add-to-dashboard.png,window=ea-images]

This workflow allows SREs to dynamically construct useful dashboards through natural language — no need to hand-craft PromQL queries or manually configure chart panels. As investigations evolve, charts can be added incrementally, building a living dashboard that captures the metrics most relevant to the issue at hand. These dashboards persist beyond the chat session and continue to show updated metrics, serving as a reference for ongoing monitoring or future incidents.

=== Exercise 4: Enable Automatic Agentic Runs from Alerts

By default, the agentic alerts adapter runs in the cluster but does not process alerts. In this exercise, you will enable automatic investigation of critical alerts and review the agent's proposed remediation.

. Enable the alerts adapter to process critical alerts:
+
[source,sh,role=execute]
----
oc get configmap alerts-adapter-config -n openshift-lightspeed -o json \
  | jq '.data["config.yaml"] |= gsub("# +- critical"; "    - critical")' \
  | oc apply -f -
----

. The critical alerts you confirmed earlier (`PaymentErrorRateHigh` and `PodDisruptionBudgetLimit`) will now be automatically detected by the agentic system, analyzed, and remediation plans generated for each one.

. Navigate to the *Agentic Runs* UI to see the investigations in progress. The runs may initially be in the *Analyzing* phase — you can watch the agent work in real time as it queries cluster state, correlates data, and builds its findings.
+
image::agentic-troubleshooting-agentic-runs-list.png[Agentic Runs UI showing investigations,link=_images/agentic-troubleshooting-agentic-runs-list.png,window=ea-images]

. You can also manage AgenticRuns from the command line using the `oc agentic` CLI plugin. List all runs:
+
[source,sh,role=execute]
----
oc agentic run list
----
+
Get the details of the `PaymentErrorRateHigh` run:
+
[source,sh,role=execute]
----
oc agentic run get $(oc agentic run list -o json | jq -r '.items[].metadata.name' | grep -i payment | head -1)
----
+
The `oc agentic` CLI supports the full lifecycle of AgenticRuns: approve or deny proposed remediations (`oc agentic run approve` / `oc agentic run deny`), watch live agent logs (`oc agentic run logs`), or create a new run on demand (`oc agentic run create`). Run `oc agentic --help` to explore all available commands.

. Once an AgenticRun moves to the *Proposed* phase, open the run corresponding to the `PaymentErrorRateHigh` alert to drill into the step-by-step findings and remediation plan.
+
image::agentic-troubleshooting-agentic-run-detail.png[AgenticRun detail for PaymentErrorRateHigh with proposed remediation,link=_images/agentic-troubleshooting-agentic-run-detail.png,window=ea-images]

. Review the proposed remediation steps. Select the option that recommends rolling back to the last known good version — and click the *Execute remediation* button to authorize the change. It will ask you once again to confirm the execution. Click *Execute Remediation* once more to confirm.

. Once the remediation is executed, review the post-execution summary.
+
image::agentic-troubleshooting-execution-complete.png[AgenticRun with execution summary,link=_images/agentic-troubleshooting-execution-complete.png,window=ea-images]
+
NOTE: The remediation may show errors and move into the *Escalating* state. The underlying issue should still be resolved — return to *Observe > Alerting* to verify the `PaymentErrorRateHigh` alert has stopped firing. The escalation workflow is designed for cases where automated remediation is insufficient, allowing operators to open a support case with the diagnostic details collected during the investigation.

This is the full agentic loop — from alert detection through investigation, proposal, approval, and execution — with a human in the loop at every decision point. The system handles the heavy lifting of data correlation and remediation execution, while the operations team retains full control over what changes are made to the cluster.

== Key Takeaways

* Lightspeed's troubleshooting mode provides AI-driven root cause analysis through natural language conversation
* The AI correlates Prometheus metrics, pod logs, and Kubernetes resource state to identify issues
* Inline Perses charts can be generated during troubleshooting and exported to persistent dashboards
* The agentic alerts adapter enables autonomous investigation of critical alerts without human initiation
* All proposed remediation actions require explicit approval before execution
